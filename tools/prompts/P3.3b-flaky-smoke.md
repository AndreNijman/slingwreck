Fix the flaky assertion in `tools/smoke.mjs`. This is a gate-integrity bug and it
matters more than any feature currently outstanding.

## The measurement

Four consecutive `npm test` runs, unchanged code:

```
run 1: PASS (22/22)
run 2: FAIL  20. portrait touch shot settles with score and pig damage: phase aiming; score 200; pigs dead 0/3
run 3: FAIL  20. portrait touch shot settles with score and pig damage: phase aiming; score 200; pigs dead 0/3
run 4: PASS (22/22)
```

A 50% flake rate. The handoff note for the last task described this as "timing-sensitive
and missed on two earlier runs before passing unchanged" and shipped it anyway. A gate
that fails half the time on correct code gets ignored within a week, and an ignored gate
is worse than no gate because it produces false confidence.

## The diagnosis

The simulation is fully deterministic, and the score is `200` on both the passing and
failing runs — so the shot is being fired, and it is landing somewhere slightly
different each time. The input is what varies, not the physics.

The cause is a race with the camera. The test presses at a fixed **screen** coordinate,
but the camera is still easing through its `panTo` transition when the press happens.
`screenToWorld` therefore maps that same pixel to a different world position depending
on how many milliseconds of easing have elapsed, which depends on machine load. The
resulting draw vector differs run to run, and in portrait — where the framing is
tighter and the same pixel error is a larger world error — that is the difference
between clipping a pig and missing it.

## The fix

**Do not weaken the assertion.** "The shot kills a pig" is the correct thing to assert
and dropping it to "the score went up" would hide exactly the class of regression this
test exists to catch.

Remove the race instead. Both of these, not one:

1. **Wait for the camera to be stable before pressing.** Poll until the camera's
   position and zoom stop changing between frames — expose a minimal read-only hook if
   one is not already available, guarded the same way the existing test hooks are — with
   a timeout and a clear message if it never settles. This is the "poll for the
   condition you actually want" rule from the original brief, applied to a condition
   that was missed.

2. **Aim in world space, not screen space.** Decide the shot as a world-space draw
   vector, then convert it to the screen coordinates to press and release, using the
   camera state at the moment of pressing. The desktop and portrait runs should then be
   firing the *same shot* at two viewports, which is a far stronger test than two
   viewports each firing whatever their pixel offsets happen to produce.

Apply the same treatment to the desktop path even though it currently passes — it is
racing too and is simply winning more often.

## Acceptance

Run `npm test` **eight** times in a row. All eight must pass, and the assertion-20 line
must report an identical score and identical pig-death count on every run. Paste those
eight result lines in your report.

If any run differs, the race is not fixed; do not report success on a smaller sample.

Write only `tools/smoke.mjs` and, if strictly necessary, a guarded read-only test hook
in `game.js`.
