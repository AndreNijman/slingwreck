Write `tools/playtest.mjs` for SLINGWRECK. It is the P3 gate. Read `docs/BUILD_PLAN.md`
P3, `tools/sim-test.mjs` and `tools/state-shots.mjs` first.

## What it is, and what it is not

`tools/sim-test.mjs` already asserts that each of the eight abilities measurably changes
the outcome. **Do not duplicate that.** This tool answers a different question: *what
does each critter actually do, and is any of it obviously wrong?*

It fires every critter into a **standard test fortress** and produces two things:

1. **A telemetry table** — one row per critter, columns for damage dealt to each
   material, pigs killed, blocks destroyed, blocks knocked off the plot, score, time to
   settle, and how far the shot travelled. Printed as a table so an outlier is visible
   at a glance.
2. **A screenshot per critter** into `shots/`, taken a moment after impact when the
   damage is visible but the rubble has not finished falling, because that is the frame
   that shows what the ability did.

Run it headless with the real renderer, the same way `tools/state-shots.mjs` does.

## The standard fortress

One fixture, used by every critter, so the rows are comparable. It must contain enough
of everything for the table to mean something: a glass upper storey, a wood frame, a
stone base, an iron piece, a TNT crate, a gel block shielding something, a spring, and
at least four pigs including a King and one behind cover. Build it so that no single
critter trivially wins — if `lob` clears the whole thing, the fixture is too fragile to
compare anything.

Fire each critter from the **same draw vector**, tapping at the same point in flight, so
the only variable is the critter. Also run each one **untapped** and put both rows in
the table, since the difference is the interesting part.

## It is a gate, so it must be able to fail

`node tools/playtest.mjs --all` exits non-zero when:

- any critter throws, or its shot produces a `NaN` anywhere in the world;
- any critter's tapped and untapped rows are **identical** — that means the tap did
  nothing, and it is the failure this tool exists to catch;
- any shot fails to settle within `TUNE.settleTimeout`;
- the browser reports a console error, a page error or a failed request.

It must **not** fail on a critter merely being weak or strong. Balance is a judgement,
and encoding today's numbers as a threshold would turn every future tuning change into
a test failure. Print the numbers; do not grade them.

## Flags

- `--all` — every critter, the gate form.
- `--ammo <id>` — one critter, for looking at a single behaviour.
- `--no-shots` — skip the screenshots, for a fast telemetry-only run.

Also support pinning a critter from the page itself with a `?ammo=<id>` query parameter
in `game.js`, guarded so it is inert without it, so a human can open the game and play
a single ability by hand. That is how the equivalent tool in `bop` gets used and it is
worth more than any table.

## What to look for and report

After it runs, read your own table and say what is surprising. Specifically:

- Is any ability strictly worse than not tapping? That is a bug, not a balance issue.
- Is any ability doing nothing to the material it is supposed to counter — `spike`
  against stone, `chip` against glass, `lob` against clusters, `pebble` against the
  thing behind the wall?
- Does `hulk` actually push a structure apart, or does it just bounce?
- Does anything settle suspiciously slowly?

Report the table and your reading of it. Do not fix balance numbers in this task — flag
what looks wrong and leave it for `tools/balance.mjs`.

## Acceptance

1. `node tools/playtest.mjs --all` passes and writes one screenshot per critter.
2. Demonstrate it can fail: temporarily neuter one ability so tapped and untapped match,
   show the failure and the message, then restore. Report both outcomes.
3. `node tools/check.mjs`, `npm test`, `npm run test:audio` all still pass.
