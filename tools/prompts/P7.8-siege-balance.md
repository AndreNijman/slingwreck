## Design

### Two sweeps, not one

**1. The parity sweep — per-card round win rate.**

"At parity" has to mean exactly this, or the number measures the wrong thing:

- Both sides at the **same round index**, the **same scrap budget** (no deficit bonus,
  no early-lock banking), and the **same bot difficulty**.
- Side A holds **exactly the one card under test**; side B holds **nothing**.
- **The live draft is disabled for this sweep.** The real draft only gives cards to the
  round loser, with tier scaling by deficit. A naive "play matches and tally holders"
  measures the comeback mechanic, not card power, and produces a clean-looking table of
  a number nobody asked for.
- **Mirror every pairing.** Run each pairing twice with the card on P1 and on P2, same
  seeds otherwise, so any structural side bias cancels. Report the unmirrored split too
  — if P1 and P2 win rates differ materially with *no* card in play, that is a defect in
  the round, not in a card, and the harness should surface it. Include a **null pairing**
  (neither side holds anything) as the control, and print its win rate. If the control is
  not near 50%, every card number in the table is suspect and the run must say so.

A siege round makes each player simultaneously attacker of the opponent's fortress and
defender of their own, so a card holder's loadout goes in as `attackerCards` for their
own assault world and as `defenderCards` for the opponent's assault world. Get this
wiring right; it is the difference between measuring a card and measuring nothing.

**2. The natural sweep — win-condition distribution.**

Full rules: real `rollDraft`/`defaultDraftPick` to the round loser, deficit budgets via
`budgetFor`, early-lock banking, sudden death, `matchWinner`. This is the sweep the 70%
rule is measured on, because it is the only one that reflects the mode as designed.
Tally `resolveRound`'s `reason` across every round: `king-pop`, `score`,
`sudden-death-damage`, `fortress-cost`, and any unresolved outcome.

### `-n`

`-n N` is **the number of matches in the parity sweep**, default 400. The natural sweep
runs `max(50, ceil(N / 4))` matches. Print both counts, the total rounds simulated in
each, and the **per-card sample size** that falls out of the allocation. Allocate parity
matches round-robin across the 25 cards so the per-card counts differ by at most one.

Print each card's round win rate **with its sample size and a binomial 95% confidence
interval**. Flag on the point estimate, because that is what BUILD_PLAN says — but where
a flagged card's interval straddles the threshold, mark the row so a reader knows the
flag is inside the noise. Do not move the threshold to make a row comfortable.

### Build-affecting cards must actually be expressible

`bots.js` `fortressForBudget(budget, templateIndex)` is card-blind: it takes a plain
number and walks a fixed template. Cards whose effect kind changes what can be *built* —
extra budget, cheaper or unlocked materials, extra pigs, Decoy/Flak/Understudy flags,
plot tilt — will report ~50% and look balanced when in truth they were never exercised.
The repo standard is explicit: an effect that does nothing measurable is a bug, and a
report is a claim rather than evidence.

So the harness must route the bot's fortress through the card-aware build path:
`fortressForBudget` for the seed blueprint, then `fromBlueprint(blueprint, { cards, round })`,
then spend any remaining scrap with `place()` until the budget is exhausted, then
`validate()` and `settleTest()` before it is used. Every blueprint entering a measured
round must pass the same Siege `validate` the relay enforces; a rejected blueprint is a
harness bug, not a result to average in, and must abort the run with the reason and the
piece ids.

Then, for each of the 25 cards, assert the harness's own coverage: that holding the card
demonstrably changed at least one observable of the round it was used in (budget, piece
count, bag contents, ammo pool, plot, score components — whatever that effect kind
touches). Print a coverage table. **Any card the harness cannot express must be listed
by name under an explicit "unexercised" heading and must make the run exit non-zero.**
Silently averaging an inert card is the failure mode this clause exists to prevent.
`tools/siege-test.mjs` already proves 25/25 cards change a measured outcome — read
`cardMeasurement()` there and reuse its approach rather than inventing a second one.

## Thresholds — fixed, not negotiable

- Card holder round win rate **> 65%** → flag.
- Card holder round win rate **< 40%** → flag.
- **> 70%** of natural-sweep rounds resolving on points rather than a King pop → the
  gate fails and reports it as a design finding.

These three numbers come from BUILD_PLAN. A threshold adjusted after seeing the
measurement is not a gate, it is a record of one run — the pyramid test in P1 shipped a
0.75 limit because the structure moved 0.54, and the structure was broken. If the run
comes back red, **report it red**. A red P7.8 that names which cards and by how much is
the correct outcome of this task and is worth more than a green one.

## Determinism

- Seeded throughout. Use the project's existing `rng` (xorshift32) and **never seed 0** —
  zero is that generator's absorbing state and it returns 0 forever; seeds derive from
  match state, so it is not hypothetical.
- No `Date.now()`, no `Math.random()`, no wall-clock in anything that affects a result.
  Timing may appear in the throughput line only.
- **Two consecutive runs at the same `-n` must produce byte-identical output** apart from
  the elapsed-time line. Verify this and paste both hashes.
- The simulation modules are under the determinism purity rule; `node tools/check.mjs`
  enforces it and must stay green.

## Output

Print measured values, not verdicts — `stack drift 0.000075 < 0.02` is debuggable,
`PASS` is not. The run should produce, in order:

1. Configuration echo: n, derived counts, seeds, bot difficulty, per-card sample size.
2. The control/null pairing win rate and the P1-vs-P2 side check.
3. The 25-card table: card id, tier, effect kind, rounds played, holder round win rate,
   95% CI, flag state.
4. The card-coverage table, and the unexercised list if any.
5. The win-condition distribution over the natural sweep — counts and percentages for
   every reason, plus the King-pop share against the 70% rule.
6. A summary line and the throughput (rounds/second).

Exit non-zero if any card is flagged, any card is unexercised, the King-pop rule fails,
the control pairing is not near 50%, a blueprint fails validation, or a match fails to
terminate.
