## The one structural fact that shapes everything

**The two players' worlds never interact.** You attack their fortress, they attack yours.
So there is no authoritative 60 Hz simulation of both worlds — the relay is authority for
the *build* phase and an *auditor* of the siege phase. That is the whole reason this relay
is cheap. Put that in a comment at the top, as `bopl/worker.js` does.

## net.js — 150 lines, client side

One websocket. Relay resolution order, matching the family convention:

1. `?relay=` query parameter
2. `window.SLINGWRECK_RELAY_URL`
3. `location.origin` when on localhost
4. hardcoded fallback `https://slingwreck-relay.tung-tung-tung-sahur.workers.dev`

**No automatic reconnect during a round.** §5 permits reconnect for this game because a
round is reconstructible from `(blueprint, seed, shot log)`, but that is a deliberate
resume in the next task, not a silent retry loop. Expose the connection state so the UI can
say what is happening.

## worker.js — `LobbyRegistry`

A single instance addressed by name `'global'`, holding the public lobby directory with
heartbeat and staleness expiry. `REGISTRY_HEARTBEAT` 10 s, `REGISTRY_STALE` 30 s. Rooms
that stop heartbeating disappear from the list rather than lingering — `bop` shipped a bug
here and had to fix it, so expire on read as well as on a timer.

## worker.js — `SiegeRoom`

One instance per room key. Endpoints:

```
GET /health    liveness
GET /lobbies   public lobby directory
GET /ws?room=  websocket; the first message must be create or join
```

Constants in the shape `bopl` uses: `ROOM_TTL` 45 min, `HANDSHAKE_MS` 12 s,
`MAX_MESSAGE` 8192 — larger than `bop`'s 4096 because a blueprint is about 370 bytes
encoded and a preview frame is bigger than an input packet.

Security, all of it, because this is a public endpoint:

- **Origin allowlist**: production origin, `*.andrenijman.com`, `*.workers.dev`, and
  localhost. Reject anything else before upgrading.
- **Room passwords hashed with SHA-256** and compared in constant time. Never store or log
  a plaintext password.
- `cleanName()` — printable ASCII only, length capped, for player and room names.
- Message size cap, handshake timeout, and a per-IP rate limit on password attempts.
- Two players maximum. `docs/DESIGN.md` §9 says no more, and the mode does not work with
  three.

## The build phase — the relay is authority

On lock-in each client sends its blueprint as the compact string from `build.js`.

The relay then, per §5:

1. `decode`s it, rejecting malformed input with a reason rather than throwing — it is being
   fed hostile data by definition.
2. `validate`s it in `'siege'` mode against that player's budget and cards, including
   burial depth and the piece limits.
3. Runs `settleTest` to confirm it stands and its pigs survive.
4. On success, sends the **authored** blueprint to the opponent — *not* the settled state.
   Both clients settle it themselves and reach the identical state because the simulation
   is bit-identical across engines. This is what the P1 and P3.1 determinism work bought;
   do not put settled poses on the wire.
5. On failure, returns the error codes and offending piece ids to the sender only, so they
   can fix it, and does not reveal anything to the opponent.

Both blueprints locked, or the build timer expiring, moves the room to the siege phase. A
player who never locks in gets their draft auto-completed to legality, per §6.2.
